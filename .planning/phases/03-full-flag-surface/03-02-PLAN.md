<objective>
Add display-width-aware word wrapping (RENDER-05). The message is wrapped to 40 display columns by default; `RenderOpts.Width` overrides the width; `RenderOpts.NoWrap` disables wrapping. Long words that exceed the width are hard-broken mid-word at rune boundaries (Perl-cowsay behavior, D-02). Existing newlines are preserved, then each resulting line is wrapped (D-04). Wrapping shares the `displayWidth` primitive from Plan 01 so a CJK string wraps and sizes consistently (D-03).

This slice changes `buildBalloon` to accept already-wrapped `[]string` lines (per RESEARCH open question 3) and inserts the wrap step in `Render`. After this slice, a long message rendered through `Render` produces a multi-line bubble no wider than 40 columns. CLI flags `-W`/`-n` that drive these options are wired in Plan 04.

Purpose: Word wrap (RENDER-05, ROADMAP success criterion #1).
Output: New `wrap.go` helper file; `RenderOpts` gains `Width int` + `NoWrap bool`; `buildBalloon` signature becomes `buildBalloon(lines []string, think bool)`; `Render` wraps before building the balloon; wrap unit tests + a wrapped golden.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| message (stdin/argv) → wrapMessage | Untrusted text drives word splitting and the hard-break loop |
| RenderOpts.Width → wrap loop | Width value (later from -W) controls the per-line column budget |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03 | Denial of Service | wrapWords/hardBreak loops over very large input | accept | Both loops are O(n) over the message; no allocation amplified beyond input length. Total work is bounded by input size already read from stdin. |
| T-03-04 | Denial of Service | tiny or zero width (Width=1, or via -W later) causing pathological line counts | mitigate | hardBreak has a safety break when a single rune is wider than width (prevents infinite loop on width smaller than one rune). Width<=0 is treated as no-wrap/default-40 in Render (Pitfall 6), so negative/zero never reaches the loop. Output line count is bounded by input length, not by an unbounded multiplier. |
| T-03-05 | Tampering | adversarial Unicode (combining/zero-width/wide) through wrapWords + hardBreak | mitigate | hardBreak advances by utf8.DecodeRuneInString byte size, never by display width, so it never slices inside a rune; chunks are always valid UTF-8 (asserted by TestHardBreak_RuneSafe). |
</threat_model>
